# Deployment instructions to hand to an AI

> Chinese version: [AI_DEPLOYMENT_PROMPT.md](AI_DEPLOYMENT_PROMPT.md)

## The user only has to buy two things

Any vendor works; never hard-code one cloud provider:

1. A paid, always-on "lightweight application server" or ordinary VPS: Ubuntu 22+, Debian 11+, Fedora 44+, CentOS Stream/RHEL/Rocky/AlmaLinux 9+ and other common x86_64 systems, at least 1 vCPU, 1 GB RAM and 20 GB disk, and explicitly a dedicated public IPv4. Buy a monthly or yearly instance; do not buy preemptible, spot, Windows, database, GPU, pre-installed-panel, custom Alpine image, or second-device-keepalive plans.
2. A paid domain that the user owns long term: any registrar and any suffix, with common suffixes such as `.com` recommended. No separate SSL certificate, CDN, premium DNS plan, enterprise mailbox, or website package is needed.

Once the purchases are done, the user opens the server console and the domain console on the computer and sends the whole block below to an AI that can operate a browser and a terminal. The user does not need to look up or enter IPs, ports, DNS records, keys, or certificates.

> Please complete the Snow App phone public WAN remote-control deployment for me directly.
>
> I have already bought a long-running public Linux server and a paid domain. The cloud vendor and the registrar are not fixed, so first look at the consoles I currently have open and identify the server vendor, region, public IPv4, SSH login method and the domain; do not assume I use Alibaba Cloud, and do not make me understand or hand-fill technical parameters such as Caddy, PEM or TLS names.
>
> Please do the following work:
>
> 1. Confirm that the server is a supported x86_64 Linux (Ubuntu 22+, Debian 11+, Fedora 44+, CentOS Stream/RHEL/Rocky/AlmaLinux 9+) with a dedicated public IPv4, and that it is not a preemptible or spot instance.
> 2. In the domain console, create one `snow` A record pointing to the server public IPv4; no `frp` record is needed.
> 3. In the cloud firewall or security group, allow TCP 22, 80, 443 and the SSH2 tunnel port (default 7001); do not expose the loopback port (default 18080) to the internet.
> 4. Do not install the tunnel service manually: Snow "Settings -> Mobile remote control -> First-time setup" installs the restricted sshd and Caddy over SSH and generates the dedicated key. In Snow, fill in the public IP, root domain, SSH login method and tunnel port, then click "Check DNS" and "Deploy and connect".
> 5. Check that `snow-tunnel-sshd.service` and Caddy are running, that the loopback port (default 18080) listens only on `127.0.0.1`, and confirm the public link works.
> 6. Finally, remind me to turn off Wi-Fi on the phone and scan the public QR code over the cellular network for acceptance.
>
> Keep working until the deployment is complete. Pause only for payment, login, CAPTCHA, identity verification, or a server password that I must type myself. Do not ask me to paste the SSH password, private keys, or configuration contents into the chat.

The AI should operate the console that matches the actual vendor and must not ask the user to copy professional parameters out of the page one by one. Only when the built-in Snow deployer is really unavailable, use the manual fallback command below (the dedicated public key must be generated by Snow first):

```bash
# Optional parameters: --tunnel-port <SSH2 tunnel port> --remote-port <loopback port> --lang en|zh-CN
sudo bash install-ssh2.sh \
  --public-domain snow.example.com \
  --tunnel-port 7001 \
  --remote-port 18080 \
  --pubkey-file /tmp/snow.pub
```

The script supports x86_64 Ubuntu 22+, Debian 11+, Fedora 44+ and CentOS/RHEL/Rocky/AlmaLinux 9+ systems; it pins the Caddy download hash, writes the restricted sshd configuration, a dedicated host key and the Caddy site configuration, and prints root-only tunnel metadata. The script never pays for or buys the server or the domain on the user's behalf.
